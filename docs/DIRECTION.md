## 3. 기술 스택 — Electron

### 3.1 선택 근거

까다로운 두 가지(`.lnk` 파싱, 아이콘 추출)를 **Electron이 이미 내장 API로 제공한다.**

| 요구 | API | 비고 |
|---|---|---|
| `.lnk` 읽기 (target/args/icon/iconIndex) | `shell.readShortcutLink(path)` | Windows 전용 |
| `.lnk` 생성·수정 | `shell.writeShortcutLink(path, op, options)` | Windows 전용 |
| 아이콘 추출 | `app.getFileIcon(path, {size})` → `NativeImage` | small 16 / normal 32 / large |
| 모니터 목록·좌표 | `screen.getAllDisplays()` | 좌/우 배치 계산에 사용 |
| 전역 핫키 | `globalShortcut.register()` | 단, 아래 3.3 제약 |
| 프레임리스 사이드바 | `BrowserWindow({frame:false})` + `alwaysOnTop` + `setBounds` | |
| 드래그&드롭 | HTML5 DnD | |

그룹화·재배치 UI는 웹 기술이 가장 쉽다. C#/Rust로는 같은 UI에 몇 배의 품이 든다.

### 3.2 검토했으나 채택하지 않은 스택

- **Tauri** — 번들은 가볍지만 `.lnk` 파싱·아이콘 추출을 직접 구현해야 한다
- **C# WPF** — Win32 API 접근은 쉬우나 드래그 그룹화 UI 비용이 크다
- **AutoHotkey 단독** — 복잡한 UI에 부적합

### 3.3 알려진 한계 — Win 키 대체

**`globalShortcut`은 수식키 단독 등록이 불가능하다.** `Win+Space`는 되지만 `Win` 하나만은 안 된다.

Win 키 단독을 가로채려면 `WH_KEYBOARD_LL` 저수준 훅이 필요하고, 다음 함정이 있다.

- Win down을 삼키면 `Win+E` `Win+R` 등이 전부 죽는다. 조합/단독 판별은 **keyup 시점에야 가능**하므로, 조합이면 `SendInput`으로 재주입해야 한다
- down만 막고 up을 안 막으면 Win 키가 **눌린 상태로 고착**된다. 대칭으로 막아야 한다
- `Win+L` `Win+G` 등은 훅으로 막을 수 없다 (레지스트리 정책 필요)
- 훅 콜백이 `LowLevelHooksTimeout`을 초과하면 **윈도우가 조용히 훅을 해제**한다. 콜백 안에서 UI 작업 금지
- 관리자 권한 창 위에서 동작하려면 훅 프로세스도 elevated 여야 한다
- 자기 `SendInput`이 훅에 재귀 진입하므로 `LLKHF_INJECTED` 검사 필요

**결정: Win 키는 나중에 붙인다.** 본체를 먼저 완성한다.
붙일 때도 훅을 직접 짜기보다 **AutoHotkey 보조 프로세스에 Win 키 판별만 위임**하는 쪽을 우선 검토한다.
(참고: StartAllBack은 explorer.exe에 후킹한다. Electron으로는 재현 불가한 방식이다.)

### 3.4 컨텍스트 메뉴 "Blueming Menu 에 등록"

드래그&드롭만으로는 사이드바가 숨어 있을 때 등록이 불편하다. 탐색기에서 바로 넣을 수 있는 경로를 둔다.

**구현 — 레지스트리 방식 (채택)**

```
HKCU\Software\Classes\lnkfile\shell\BluemingMenu.Add
    (기본값) = "Blueming Menu 에 등록"
    Icon     = "<앱경로>\BluemingMenu.exe,0"
HKCU\Software\Classes\lnkfile\shell\BluemingMenu.Add\command
    (기본값) = "<앱경로>\BluemingMenu.exe" --add "%1"
```

- `HKCU`라서 **관리자 권한이 필요 없다**
- 대상 확장: `lnkfile`(바로가기) · `exefile`(실행파일). 폴더(`Directory`)는 추후 판단
- 앱이 이미 떠 있으면 단일 인스턴스로 인자를 전달하고, 아니면 실행 후 등록

**Windows 11 제약 (실측 확인)**

레지스트리 방식으로 등록한 항목은 **기본 우클릭 메뉴에 안 나오고 "추가 옵션 표시" 하위로 들어간다.**
`Shift`+우클릭이면 바로 접근된다.

1급 메뉴에 올리려면 `IExplorerCommand` COM 핸들러(네이티브 DLL) + Sparse MSIX 패키지 + 인증서 서명이 필요하다.
**JavaScript로는 구현 불가**이며, 별도 네이티브 모듈과 패키징 파이프라인이 든다.
1단계에서는 하지 않는다. 실사용 후 불편하면 그때 재검토.

**이 PC 실측 (2026-08-18)**

- `HKCU\...\CLSID\{86ca1aa0-34aa-4e8b-a509-50c905bae2a2}` 없음 → **Windows 11 모던 메뉴 사용 중**
- `lnkfile` · `exefile` · `*` 에 커스텀 verb **0개** (깨끗함, 충돌 없음)
- 참고: 모던 메뉴가 불편하면 위 CLSID 키를 만들어 클래식 메뉴로 되돌리는 우회가 있다.
  24H2에서 deprecated 됐으나 25H2(26200)에서도 동작 보고가 있다. **사용자 선택 사항이며 앱이 임의로 건드리지 않는다.**

### 3.5 창 배치 — 시작 메뉴 위치 재현

**이 PC 실측 (2026-08-18)**

```
작업표시줄   TaskbarAl = 0        → 왼쪽 정렬 (중앙 아님)
             StuckRects3[12] = 3  → 화면 하단
             높이 40px

DISPLAY1 (보조)  Bounds X=-1834 Y=0  1834x1032   WorkArea H=992
DISPLAY2 (주)    Bounds X=0     Y=0  1834x1032   WorkArea H=992
```

→ 시작 버튼이 **좌하단**에 있으므로 패널은 화면 **왼쪽 아래**에서 올라온다.

**구현 지침**

- 위치는 `screen` 의 **`workArea` 를 쓴다.** 작업표시줄이 이미 제외된 사각형이라 높이를 직접 빼지 않는다
  ```
  const wa = display.workArea          // {x, y, width, height}
  x = wa.x + margin                    // 왼쪽 정렬일 때
  y = wa.y + wa.height - panelHeight   // 아래에서 위로
  ```
- **작업표시줄 설정은 런타임에 읽는다.** 정렬(좌↔중앙)·위치(하단↔상단)·높이가 바뀌면 배치도 따라가야 한다.
  하드코딩 금지

**⚠️ 반드시 지킬 것 (이 PC 특유의 함정)**

1. **보조 모니터 X 좌표가 음수(-1834)다.** 주 모니터 기준 상대 계산을 하면 창이 화면 밖으로 나간다.
   `screen.getAllDisplays()` 가 주는 `bounds` 를 그대로 써야 한다
2. **양쪽 모니터 모두에 작업표시줄이 있다.** "주 모니터에만 있다"고 가정하지 말 것
3. 논리 해상도 1834x1032 → **DPI 스케일이 걸려 있다**(150% 추정).
   Electron 은 논리 픽셀 기준으로 동작하지만, 물리 픽셀이 필요한 계산에서는 `display.scaleFactor` 를 반영할 것

### 3.6 다국어 — 한국어 · 영어 (2026-08-18 결정)

지원 언어는 **한국어(`ko`) · 영어(`en`) 2개.** 기준 언어는 `ko`, 폴백은 `en`.

**라이브러리 — i18next (채택)**

자체 경량 JSON 방식도 검토했으나 i18next 를 택했다. 언어가 더 늘거나 문자열이 수백 개로
불어날 때 폴백 체인·보간·복수형을 다시 만들 필요가 없다.

- 메인 프로세스와 렌더러 프로세스가 **각각 init 한다.** 두 프로세스는 메모리를 공유하지 않는다
- 언어 변경은 **메인이 단일 진실원(source of truth)** 이고, IPC 로 렌더러에 통보한다
- 번역 리소스 JSON 은 양쪽이 같은 파일을 import 한다

**언어 결정 — OS 자동 감지 + 설정에서 변경**

```
최초 실행  app.getLocale() → 'ko-KR' 로 시작하면 ko, 그 외 en
이후       사용자가 설정에서 고른 값이 있으면 그것을 우선한다 (자동 감지보다 위)
```

- 사용자가 한 번 고르면 그 선택을 기억한다. 이후 OS 로케일이 바뀌어도 따라가지 않는다
- 저장 위치는 설정 저장소 결정(5.1)을 따른다. **그때까지 언어 설정도 영속화하지 않는다**

**컨텍스트 메뉴 문구 — 앱 언어 따라 재등록**

3.4 의 레지스트리 문구는 앱 언어를 따라간다.

| 언어 | `HKCU\...\BluemingMenu.Add` 기본값 |
|---|---|
| `ko` | `Blueming Menu 에 등록` |
| `en` | `Add to Blueming Menu` |

- 언어를 바꾸면 **레지스트리를 다시 쓴다.** 탐색기가 이미 읽어둔 값은 즉시 안 바뀔 수 있다
  (필요 시 탐색기 재시작 안내 — 강제 재시작은 하지 않는다)
- 앱 이름 `Blueming Menu` 자체는 **고유명사라 번역하지 않는다.** 양쪽 문구에 그대로 들어간다

**적용 규칙**

- **사용자에게 보이는 문자열은 처음부터 전부 리소스로 뺀다.** 코드에 한글/영어를 직접 쓰지 않는다
  (나중에 걷어내는 비용이 훨씬 크다는 것이 이 결정을 1단계 착수 전에 한 이유다)
- 로그·에러 메시지 등 **개발자만 보는 문자열은 번역 대상이 아니다**

> **트레이 상주 (2026-08-18 확정)**

> `window-all-closed` 에서 `app.quit()` 을 부르면 이 요구가 깨진다.
> **종료 경로는 트레이 메뉴뿐이다.** 포커스 상실로 패널이 닫히는 것과 앱 종료는 별개다.
> 트레이 아이콘은 `.ico` 를 쓴다 — DPI 스케일 환경에서 단일 PNG 는 뭉갠다.

### 2단계 — 편집
- 드래그&드롭으로 항목 추가
- 드래그&드롭으로 그룹 만들기·이동·이름변경
- 설정 저장/복원
- 컨텍스트 메뉴 "Blueming Menu 에 등록" 연동

### 3단계 — 다듬기
- 검색창
- 단축키 지정 UI
- 열림/닫힘 애니메이션 (시작 메뉴처럼 아래에서 위로)
- 설정 UI
- **언어 선택 UI** (ko/en 전환 + 컨텍스트 메뉴 문구 재등록)

> 다국어(3.6)는 3단계 항목이 아니다. **1단계부터 모든 UI 문자열을 리소스로 뺀다.**
> 3단계에서 붙이는 것은 "전환 UI" 뿐이다.

## 5. 미결정 — 사용자 판단이 필요한 것

**이 항목들은 임의로 정하지 않는다.** 근거 없는 값을 코드에 넣지 않는다는 원칙에 따른다.

### 5.1 데이터 — **결정됨 (2026-08-18)**

**한 번 가져오고 그 뒤로는 독립 관리한다.**

- `Programs` 폴더를 실시간 추종하지 **않는다.** 최초 1회 임포트한 뒤 자체 데이터로 관리한다
- 새 앱은 사용자가 드래그&드롭으로 추가한다
- 원본 `.lnk` 파일은 **읽기만 한다.** 이동·삭제·수정하지 않는다

파생 사항 (구현 시 확인받을 것):
- 임포트 범위 — 205개 전부인지, 필터를 걸지. **임포트는 언제든 다시 돌릴 수 있게 만들어 결과를 보고 정한다**
- 임포트 시 폴더 구조를 그룹으로 변환할지 (`Python 3.13` 폴더 → `Python 3.13` 그룹)
- 저장 위치: 앱 폴더 안(포터블) vs `%APPDATA%`

#### 기존 시작 메뉴 그룹은 자동 이전 불가 (2026-08-18 실측)

현재 Windows 11 시작 메뉴 "고정됨"에 사용자가 만들어둔 그룹 8개가 있다.
**개발관련 · 브라우저및오피스 · AI관련 · 생활도구 · 소통및기록 · 멀티미디어 · 기타 · 시계**
(그 외 개별 항목 10여 개: 프로그램 종료_시작 · Samsung Flow 종료_시작 · 삼성 플로우 ·
Acronis True Image · IObit Uninstaller · 화면가리개 · Logi Options+ · Telegram · VS Code · NotiStar)

이 그룹 정보는 `Programs` 폴더가 **아니라** `start2.bin`에 들어 있다. 실측 결과:

```
경로  %LocalAppData%\Packages\Microsoft.Windows.StartMenuExperienceHost_cw5n1h2txyewy\LocalState\start2.bin
크기  51,340 bytes
앞16  e2 7a e1 4b 01 fc 4d 1b 9c 00 81 0b de 6e 51 85   ← 매직넘버 없음
평문  전무 (ASCII 런이 전부 난수)
```

**압축된 바이너리다.** 파싱하려면 LZ4 해제 + protobuf 스키마 역공학이 필요한데,
문서화되지 않았고 Windows 빌드마다 바뀐다. 초기 단계에 감당할 리스크가 아니다.

**결정: 초기 그룹 8개는 사용자가 앱 안에서 직접 구성한다.** 8개뿐이라 파서를 만드는 것보다 빠르다.
(진단 목적으로 start2.bin을 읽는 것과 별개로, 이 앱은 start2.bin을 **읽지도 쓰지도 않는다.**)

### 5.2 동작

**1번 요구사항 변경(사이드바 → 시작 메뉴 형태)으로 자동 해소된 것**
- ~~자동 숨김 타이밍~~ → 포커스 상실 시 닫기
- ~~화면 공간 예약(`SHAppBarMessage`)~~ → 팝업이라 불필요. **네이티브 모듈 회피**
- ~~앱 실행 후 거동~~ → 시작 메뉴와 동일하게 닫힘
- ~~가장자리 bump 복귀~~ → 해당 없음

**남은 것**
- **그룹 펼치기 방식**: 인라인 확장 / 플라이아웃 / 패널 내 화면 전환
  (현재 Win11 시작 메뉴는 폴더 클릭 시 인라인 확장. 이걸 따라갈지)
- **재현 범위**: "고정됨" 그리드만인가, "모든 앱" 목록과 검색창까지인가
- **여는 방법**: 단축키만인가, 작업표시줄 시작 버튼 클릭도 가로챌 것인가 (후자는 4단계 영역)
- **기본 단축키 값**: 미정. `Win+Space` 는 개발 중 임시값일 뿐 확정 아님

### 5.3 외형
- 패널 크기 — 현재 시작 메뉴와 같은 크기로 맞출지, 조절 가능하게 할지
- 아이콘 크기, 한 줄 개수
- 다크/라이트 (현재 환경은 다크)
